## ayugram-gmz — Прогнать шаг публикации обновления в CI целиком

**Итог: задача НЕ закрыта, помечена `blocked`.** Приёмка требует реального
прогона `win.yml` с `publish_update=true`, а это создание релиза в
`badigit/AyuGramDesktop` и перезапись `current4` в ветке `gh-pages` — то
самое место, откуда живые клиенты берут обновление. Это изменение боевого
состояния, ночью такой прогон запускать нельзя. Запустить должен человек:

```
gh workflow run win.yml --repo badigit/AyuGramDesktop --ref mods -f publish_update=true
```

### Что сделано вместо прогона

Коммит `b8e94f3891`. Три публикующих шага (`Pack and sign update`,
`Publish release`, `Update current4 on Pages`) отрепетированы локально:
`tools/ayu-update/test_publish_steps.py` вытаскивает **те же самые** сниппеты
из `.github/workflows/win.yml` (парсит `run: |` по имени шага) и исполняет их
в песочнице — одноразовый RSA-1024 ключ, поддельный `config.h` с его
публичной половиной, заглушка `gh` в PATH, локальный bare-репозиторий вместо
`gh-pages` (через `insteadOf` в подменённом `HOME`). Наружу тест не ходит и
за пределы своего временного каталога не пишет.

Репетиция нашла два дефекта — оба свалили бы прогон уже ПОСЛЕ починки
кодировки из `a3b8b91975`:

1. **Тег релиза на чужом коммите.** `gh release create` без `--target`
   создаёт тег на ветке по умолчанию репозитория, а workflow запускается с
   `--ref mods`. Добавлен `--target "$GITHUB_SHA"`.
2. **Повторный прогон той же версии падал.** Если `current4` не изменился,
   `git commit` возвращает «nothing to commit», и `set -e` красит шаг. Теперь
   коммит и push только при реальном изменении, иначе печатается
   `current4 already points at this build`.

### Что осталось и что мешало

Ночью нечем проверить ровно то, что и делает прогон боевым:

* права `GITHUB_TOKEN` (`permissions: contents: write`) на создание релиза и
  push в `gh-pages` — проверяется только живым прогоном;
* наличие и валидность секрета `AYU_UPDATE_PRIVATE_KEY` на раннере;
* существование ветки `gh-pages` в форке (шаг клонирует её без запасного пути
  — если ветки нет, шаг упадёт на `git clone`; чинить это вслепую не стал,
  ветка по описанию задачи создана вручную при релизе v7.0.10).

Решений за пользователя не принималось: обе правки — механические, смысл
шагов не меняют.
